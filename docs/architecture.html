Reusable Field Service A2A Asset

How the A2A upsell works

Two systems, one question. What each one owns, how a recommendation travels between them, and why it refuses to answer when it cannot verify a property.

The problem this solves

A technician standing in a customer's house asks a reasonable question: what else could I sell here? Answering it well needs two kinds of knowledge that live in different places.

Facts about this customer — the property's size, how many bedrooms, what security system is already fitted — are Salesforce's. They are records, they change, and Salesforce is the system of record.

Knowledge of the products — what the catalogue offers, what suits a townhome with an existing command panel — is not in Salesforce at all. It lives in a PDF catalogue that changes on its own schedule.

Earlier versions answered this with an Apex action inside Salesforce, which meant the product reasoning had to be maintained there. The A2A version splits it: Salesforce keeps the customer, a separate agent keeps the products, and neither implements the other's half.

Who owns what

Salesforce

The customer

  • Accounts and contacts
  • Properties and their fields
  • Service appointments and schedules
  • Work orders, parts, van stock
  • All access control
Property Upsell Agent

The products

  • The PDF catalogue
  • Which products suit which property
  • Page citations for every claim
  • What still needs onsite checking
  • Nothing about any customer
The load-bearing rule

The agent is never asked to look anything up. The app gathers the property facts from Salesforce and sends them. An agent that could query Salesforce itself would duplicate the integration and blur who is responsible for a wrong answer.

One upsell turn, end to end

What happens between clicking Recommend upsell products and seeing the list. Colour marks which system is working.

Steps 5 to 7 are the part people underestimate. If any of them fails, the agent is not called at all and the Copilot explains why. A recommendation with no verified property behind it is exactly what this path exists to prevent.

The seven-field contract

The two systems agree on precisely seven fields. These are what the agent treats as established fact:

  • Property_Size__c
  • Bedrooms__c
  • Bathrooms__c
  • Year_Built__c
  • Property_Type__c
  • Security_System_Base__c
  • Monitoring_Status__c

Anything else in the message — the account name, the property's own name, the job description — reaches the agent as prose, where it is treated as caller-supplied text rather than verified fact. That separation is deliberate: a caller cannot smuggle an eighth property fact in by writing it into a sentence.

Why a name-mapping layer exists

Orgs spell these differently. A custom MCP server returns propertySizeSqFt; an org exposing the custom fields directly returns Property_Size__c. Both normalise to the same entry, so neither needs a code change: 

Property_Size__c  ←  propertysize, propertysizesqft, propertysizesquarefeet,
                     squarefeet, sqft, size
Bedrooms__c       ←  bedrooms, bedroomcount, numberofbedrooms, beds
Monitoring_Status__c ← monitoringstatus, monitoring

Comparison strips the __c suffix, removes punctuation and lowercases, so Property_Size__c, propertySizeSqFt and property_size all compare equal.

Absent is not zero

A field the org did not return is left out of the payload entirely. The agent is told it is unknown and instructed not to guess it, and reports it under Onsite Verification instead. Nothing in this path ever invents a value.

Two ways in, on purpose

TriggerPathWhy
The Upsell tab button and the suggested chip, both sending the exact phrase Recommend upsell products A deterministic intent match, before the model is involved The demo cannot fail because a model declined to pick a tool
Any other wording — "what could I sell in the kitchen?" Gemini chooses recommend_upsell_products, offered beside the Salesforce tools Natural questions still work without enumerating phrasings

The delegation tool deliberately takes no arguments. The model cannot pass a property fact, a product name or a room, because the app finds the property itself. There is nothing for a model to get wrong.

Two trust boundaries

Both systems treat incoming content as data. Neither follows instructions found inside it.

Salesforce record content, entering the Copilot

A customer name or a work-order description is text somebody typed into a CRM. It arrives wrapped as tool output, quoted rather than obeyed, so a record containing "ignore previous instructions" is just a string.

The agent's reply, entering the Copilot

An agent-to-agent channel is another injection surface, so the reply is wrapped exactly as tool output is. The Copilot is instructed to keep the agent's product names and page citations verbatim, add nothing it did not state, and never let it widen the scope of the conversation.

The caller's message, entering the agent

Before each model call the agent splits the request in two: the seven whitelisted fields taken from the structured object, and everything else labelled as request text. On top of that it is instructed never to invent products, prices or specifications, never to infer sensor counts from a general system description, and to cite a catalogue page for every recommendation.

What this costs

These rules are why the system sometimes says "I couldn't look up the customer's property, so I haven't asked for recommendations". That is the design working. A system that always produces a confident list is one that guesses.

No tool names in the code

The Copilot does not know what the org's appointment tool is called. Capabilities are resolved from the published schemas returned by MCP discovery: which tool lists appointments, which sets a status, which closes a job. An org can rename its actions, or activate a custom MCP server, and nothing here needs editing.

The same idea applies across the A2A boundary. The app asks for a skill id, and falls back to matching on what the published skill says it does. A card without a matching skill fails at discovery rather than at the first request, so a misconfiguration surfaces immediately.

Environment overrides exist for orgs whose schemas say too little to infer from, but a value matching nothing leaves the capability unresolved rather than guessing.

Inside the agent

A standalone Google ADK agent with no tools. It takes no actions, calls nothing, and modifies no records. It answers one question from one document. 

A2A client  ──▶  ADK agent  ──▶  OpenRouter (via LiteLLM)
                     │
                     └── catalog/<one>.pdf   text extracted at startup

The catalogue

At startup the PDF's text is extracted page by page and placed in the agent's instructions, with page markers so citations name real pages. There is no vector store, no embedding and no chunking — the catalogue is assumed small enough for the model context.

Startup fails with an explicit message if the folder holds no PDF or more than one, if the PDF has no extractable text, or if the text exceeds the configured cap. It never falls back to invented product data.

The agent card

The protocol work is the SDK's, not hand-written. ADK's to_a2a() mounts the JSON-RPC endpoint and serves the card at /.well-known/agent-card.json. The card is then renamed, since ADK names it after the Python agent id and calls its single skill model, neither of which is useful to a caller.

Provider handling

The model provider is reached through LiteLLM, so switching between OpenRouter and Groq is an environment change rather than a code change. Two details matter in practice:

  • Models that emit reasoning traces have those stripped before the response leaves the agent, so internal deliberation never reaches a technician.
  • A provider failure is reported as a readable operator message rather than a stack trace. The app recognises that message and retries once, because free-tier endpoints drop streamed connections intermittently.

The agent client cache is dropped whenever a delegation throws. A stale client pointed at a restarted agent is far more expensive than one extra discovery call.

How it fails

Every failure names a stage, so a log line says where it broke and the technician sees something they can act on.

StageMeansRetried
not_configuredNo agent URL set for this appNo
discoveryThe card could not be resolved; the agent may not be runningYes
skillThe agent answered but offers no product recommendationsNo
requestThe task call itself failed twiceAlready retried
emptyThe agent returned nothingAlready retried
agent_modelThe agent could not reach its own model — throttled or out of quotaAlready retried

Before any of these, the property lookup can decide not to delegate: no appointment selected, no account name on the appointment, or no connected tool that returns property details. Each is reported with its reason, and no products are suggested.

If two tools would answer the same question — the agent and an upsell Apex action still published by the org — withdraw the Apex one with SALESFORCE_TOOL_BLOCKLIST. Two implementations competing for one question is a reliability problem, not a redundancy benefit.

Known limits

Worth stating plainly, because each is a real constraint on what this POC can become.

  • Salesforce is no longer the system of record for products. Recommended product names are not guaranteed to match Product2 records, so a quoting step would need a name-matching stage.
  • The catalogue is loaded whole. Fine for a few pages; a large catalogue would need retrieval rather than full context.
  • Technician sign-in is not authentication. A mapped technician ID with no password is acceptable for a controlled demo and nothing beyond it.
  • One turn takes 50-60 seconds on free-tier models, and the free quota is 50 requests per day across the whole account.
